# Task Issue — Reference

Use this once Step 1 of the main skill (type, repo, project, priority) is
done and the type is "task".

A task is a concrete, self-contained piece of work — a chore, a migration
step, a refactor — rather than a bug to fix or a new capability to design.
Keep it scoped to something someone could pick up and finish without needing
to make product decisions along the way.

## What to gather

1. **What needs to be done** — ask for a clear, concrete description of the
   work itself.
2. **Context** (optional) — ask briefly why this task exists or what larger
   effort it's part of, if that isn't obvious from the description alone.
3. **Checklist** — ask for the specific, checkable steps or outcomes that
   mean the task is complete.

Priority is gathered and resolved in the main skill's Step 1/3 — it belongs
in the GitHub Priority field, never in this body.

## Issue body structure

```markdown
## Description
<what needs to be done>

## Context
<optional: why this task exists / what it's part of>

## Checklist
- [ ] ...
- [ ] ...
```

Title convention: `Task: <short description>`.
